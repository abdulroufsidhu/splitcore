# Splitcore Dart SDK Implementation Plan (Plan 3 of 3)

> **Status: all 15 tasks complete (2026-07-13).** The full `splitcore_sdk` package (compute layer + PocketBase remote layer + `SplitcoreSdk` facade) is implemented, TDD throughout, 49/49 tests green against real dependencies (the actual linux `.so` and the actual `server` binary), `dart analyze` clean. What's left beyond this plan is the Flutter mobile app itself — see "Deferred beyond this plan" at the bottom.

**Goal:** `splitcore_sdk`, a Dart package wrapping (a) the compiled `splitcore` FFI library for split/settlement/balance math and (b) PocketBase communication, so a Flutter frontend never talks to PocketBase or does split math directly — see `docs/superpowers/specs/2026-07-06-splitcore-design.md` §5.

**Architecture:** Two independent layers under `lib/src/`: the **compute layer** (FFI bindings → isolate wrapper → `SplitcoreCalc`, done) and the **remote layer** (PocketBase client → auth/CRUD/receipts/sync → staleness-checked settlement flow, pending). Both are unified behind a single facade, `SplitcoreSdk`, exported from `lib/splitcore_sdk.dart` — the sole public surface.

**Tech stack:** Dart 3.9 SDK, `package:ffi` (done), `package:pocketbase` (official pub.dev client — decided with user, see below), `package:image` (pure-Dart receipt compression, pending), `package:test`.

## Global constraints

- Public surface exported **only** through `lib/splitcore_sdk.dart`; everything under `lib/src/` stays internal.
- Every FFI computation runs off the caller's isolate via `Isolate.run` (done — `IsolateCalc`). New remote-layer work does not need isolates (network I/O is already async); do not add isolate wrapping to PocketBase calls.
- Money is `int64` minor units everywhere; never floats.
- TDD throughout — write the test first, watch it fail, minimal code to pass (per project convention; no exceptions granted so far).
- **PocketBase client:** use the official `pocketbase` pub.dev package, not a hand-rolled HTTP client (user decision, 2026-07-13).
- **Local store:** in-memory per group, version-tagged, fetch-on-demand. No persistent cache in v1; design the interface so one can be added later without changing the public API.
- Frontend never talks to PocketBase directly — every PB interaction the SDK exposes must go through `SplitcoreSdk`, never leak a raw `PocketBase`/`RecordModel` instance across the public boundary.
- Collections/fields/rules are fixed by `server/migrations/1751760000_init_collections.go` — read it before writing CRUD wrappers so field names match exactly (`groups.currency`, `group_members.role`, `expenses.split_type`, `split_entries.receipt`, etc.).

## Domain semantics (binding, from design spec §5)

- **Pre-settlement flow:** before creating a settlement, call `GET /api/splitcore/staleness?group={id}&version={n}` (server/hooks/staleness.go). If `current: true`, proceed silently. If `false`, refetch the group's records, recompute balances locally via `SplitcoreCalc`, *then* create the settlement. Never create a settlement against known-stale local state.
- **Receipts:** downscale to a max dimension + JPEG re-encode via the pure-Dart `image` package before upload; attach the uploaded file to the `split_entries.receipt` field. Compression happens client-side — the server never resizes images.
- **Auth:** SDK owns sign-in/sign-up/sign-out/current-user against PocketBase's built-in `users` auth collection. No custom auth endpoints exist server-side.
- **CRUD scope:** groups (+ member management), expenses (create with a `SplitSpec`, update, delete), split entries (implicitly via expense create, since the server's hooks recompute balances per split_entries row — confirm against `server/hooks/hooks.go` before assuming one call creates both expense + entries), settlements (create only — no update/delete surfaced, matching the reimbursement-log model).
- **Balances:** `sdk.balances` reads the server's cached `balances` collection (read-only for clients per the API rules) rather than recomputing from scratch on every read — recompute-from-log is for local staleness-triggered resync, not the default read path.

### Task 7: PB test harness — spin up a real PocketBase instance for integration tests

**Why real, not mocked:** project convention is to run actual tests against real behavior (see `server/` test suite, which uses `tests.NewTestApp()` against real PocketBase, not mocks). The Dart PB client layer should integration-test the same way — against a real running `server` binary — so a passing test means the wire contract actually works, not that a hand-written mock agrees with itself.

**Files:**
- Create: `splitcore_sdk/test/support/pb_server.dart` — starts `go run .` (or a pre-built binary) from `../server` on an ephemeral port with a temp `pb_data` dir, waits for `/api/health`, tears down (kill + delete temp dir) in `tearDownAll`.
- Modify: `splitcore_sdk/pubspec.yaml` — add `pocketbase` dependency.

- [x] **Step 1:** `test/support/pb_server.dart` — `PbTestServer.start()` launches `go run . serve --http=127.0.0.1:$port --dir=$tempDir` from `../server`, finds a free port via an ephemeral `ServerSocket` bind, polls `/api/health` (30s timeout), `stop()` sends SIGTERM then SIGKILL-after-5s and deletes the temp dir. **Deviation:** no `PORT`/data-dir env vars needed on the server — PocketBase's built-in `--http`/`--dir` CLI flags covered it, no server-side change required. **Gotcha found and fixed:** PocketBase logs heavily on startup (SQL + request logs); the child process's stdout/stderr pipes must be drained (`process.stdout.drain()`) or the OS pipe buffer fills and the server hangs before ever binding — this caused every first-pass test to time out until diagnosed.
- [x] **Step 2:** `test/support/pb_server_test.dart` — 2 tests (health responds; two servers get isolated ports/data dirs). Both green.

**Files:** `lib/src/remote/receipts.dart` (pure `compressReceipt` + `attachReceipt` free functions), wired into `ExpensesApi.attachReceipt` (imported with an `as receipts` prefix — a same-named method and top-level function in the same file would otherwise recurse into itself unqualified).

- [x] `compressReceipt(bytes, {maxDimension: 1600, quality: 85})` downscales + re-encodes as JPEG. **Test-fixture pitfall found while writing the "output is smaller" test:** a flat-color synthetic image lets lossless PNG trivially beat any JPEG (degenerate case); a naive per-pixel modulo-noise pattern is the *opposite* degenerate case (adversarial for JPEG's DCT, ideal for PNG's deflate); even a pure smooth gradient is near-optimal for PNG's row filters. Settled on gradient-plus-bounded-noise (mimics real photo grain) as the only fixture where JPEG legitimately wins, same as it would on an actual receipt photo. 3 offline tests + 1 real-server attach test green in `test/remote/receipts_test.dart`, plus an integration test of the wired-up `ExpensesApi.attachReceipt` path.
